# Workflow

## Общие принципы

Этот документ описывает рабочий процесс разработки проекта "Оптико-электронный тренажёр для отработки стрельбы по БПЛА".

## Управление версиями

### Git
- **Ветка разработки:** `main` (основная стабильная версия)
- **Фича-ветки:** `feature/<описание>` (например, `feature/video-receiver`)
- **Исправления:** `fix/<описание>` (например, `fix/udp-timeout`)
- **Релизы:** `release/v<версия>` (например, `release/v1.0.0`)

### Коммиты
- **Частота:** После завершения каждой задачи (task)
- **Формат сообщений:**
  ```
  <тип>(<область>): <краткое описание>
  
  <подробное описание (опционально)>
  
  <резюме задачи (опционально)>
  ```
  
  **Типы:**
  - `feat` — новая функциональность
  - `fix` — исправление ошибки
  - `docs` — изменения в документации
  - `style` — форматирование, отсутствующий код (без изменения логики)
  - `refactor` — рефакторинг кода
  - `test` — добавление тестов
  - `chore` — обновление зависимостей, конфигурации
  
  **Примеры:**
  ```
  feat(network): Реализовать UDP-приёмник видеопотока
  
  Добавлен класс VideoReceiver для приёма MJPEG кадров
  по UDP на порт 5000. Поддержка неблокирующего режима
  и буферизации кадров.
  
  Задача: TR-001 "UDP Video Receiver"
  ```

## Тестирование

### Покрытие кода
- **Минимальное покрытие:** 80% для критичных модулей
- **Критичные модули:**
  - `src/detection/` — детекция и анализ попаданий
  - `src/network/` — сетевая коммуникация
  - `src/storage/` — работа с базой данных
- **Инструмент:** pytest-cov

### Типы тестов
1. **Unit-тесты:** Для отдельных функций и классов
2. **Integration-тесты:** Для взаимодействия модулей
3. **GUI-тесты:** Для интерфейса (pytest-qt)

### Запуск тестов
```bash
# Все тесты
pytest

# С покрытием
pytest --cov=src --cov-report=html

# Конкретный модуль
pytest tests/test_detection.py
```

## Разработка

### Структура задач
Каждая задача (task) в плане разработки включает:
1. **Описание:** Что нужно сделать
2. **Критерии приёмки:** Условия выполнения задачи
3. **Тесты:** Unit-тесты для новой функциональности
4. **Документация:** Обновление docstrings и комментариев

### Процесс разработки
1. **Создать фича-ветку** от `main`
2. **Реализовать тесты** (TDD — Test-Driven Development)
3. **Реализовать функциональность**
4. **Запустить тесты** и убедиться в прохождении
5. **Проверить покрытие** (≥80% для критичных модулей)
6. **Обновить документацию**
7. **Создать коммит** с описанием задачи
8. **Создать Pull Request** (если применимо)
9. **Влить в main** после ревью

### Code Review
- **Обязательно** для критичных модулей (детекция, сеть)
- **Проверка:**
  - Соответствие code style guide
  - Наличие тестов
  - Качество документации
  - Отсутствие hardcoded значений (использовать config)
  - Обработка ошибок

## Непрерывная интеграция (CI/CD)

### Автоматические проверки
При каждом коммите в `main` или Pull Request:
1. **Линтинг:** Ruff (проверка стиля кода)
2. **Тесты:** pytest (все тесты)
3. **Покрытие:** pytest-cov (проверка ≥80%)
4. **Сборка:** PyInstaller (создание .exe)

### Ручные проверки (перед релизом)
1. **Интеграционное тестирование** с реальной MaixCAM
2. **Тестирование производительности** (FPS, задержка)
3. **Тестирование на разных конфигурациях** (с GPU, без GPU)

## Документация

### Обновление документации
- **API документация:** Docstrings в коде (Google style)
- **Пользовательская документация:** README.md, USER_GUIDE.md
- **Техническая документация:** ARCHITECTURE.md, DEPLOYMENT.md

### Формат документации
- **Язык:** Русский (основной)
- **Стиль:** Формальный, технический (согласно product-guidelines.md)
- **Примеры кода:** Обязательно для сложных функций

## Релизный процесс

### Версионирование (Semantic Versioning)
- **MAJOR:** Несовместимые изменения API
- **MINOR:** Новая функциональность (обратно совместимая)
- **PATCH:** Исправления ошибок

**Пример:** `v1.2.3`

### Подготовка релиза
1. **Обновить версию** в коде и документации
2. **Создать CHANGELOG.md** с описанием изменений
3. **Создать релизную ветку** `release/v<версия>`
4. **Протестировать** на целевых конфигурациях
5. **Собрать дистрибутив** (PyInstaller + Inno Setup)
6. **Создать тег** `v<версия>`
7. **Опубликовать релиз**

### Пост-релиз
- **Обновить документацию** на сайте/в репозитории
- **Уведомить пользователей** (если применимо)
- **Собрать обратную связь** для будущих улучшений

## Мониторинг и логирование

### Логи
- **Уровень:** INFO (продакшн), DEBUG (разработка)
- **Ротация:** 10 МБ на файл, хранить последние 5 файлов
- **Формат:** `YYYY-MM-DD HH:MM:SS [LEVEL] module: message`

### Метрики (опционально)
- **Количество сессий** тренировок
- **Средняя точность** попаданий
- **Время отклика** системы
- **Использование ресурсов** (CPU, RAM, GPU)

## Безопасность

### Защита данных
- **Локальное хранение** всех данных тренировок
- **Шифрование Wi-Fi** (WPA3)
- **Проверка целостности** пакетов (checksum)

### Код
- **Не хранить** секретные ключи в репозитории
- **Использовать** переменные окружения для конфиденциальных данных
- **Регулярно проверять** зависимости на уязвимости (safety, bandit)

## Резюме

Этот workflow обеспечивает:
- **Качество кода** через тестирование и code review
- **Предсказуемость** через структурированный процесс разработки
- **Поддерживаемость** через документацию и стандарты
- **Безопасность** через проверки и мониторинг

Все участники команды должны следовать этому workflow для обеспечения успешной разработки проекта.
